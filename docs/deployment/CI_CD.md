# Изменения и обновление работающего бота

## Что подготовлено

CI запускается на pull request, push в main/work/** и вручную. Python 3.12, зависимости из Linux lock-файла с проверкой хэшей, полный pytest; затем сборка production Dockerfile и проверка /login в отдельном контейнере web без настоящего Telegram-токена и рабочей базы.

Deploy production запускается только вручную и только для main. Перед выкладкой повторяет CI для выбранного SHA. Затем подключается к серверу через отдельный SSH-ключ и запускает scripts/deploy.sh для этого же SHA. Сборка на сервере выполняется заново из проверенного коммита; готовый образ из CI не переносится, поэтому идентичность байтов двух образов не гарантируется.

Push и объединение PR сами по себе не обновляют работающего бота. Ветка с этим документом не меняет сервер до ручного запуска.

## Однократная настройка GitHub

После проверки и объединения PR откройте Settings → Environments → создайте production. Если тариф и видимость репозитория позволяют, настройте подтверждение запуска и ограничение веткой main. Сам workflow также проверяет refs/heads/main.

Добавьте четыре environment secret:

| Имя | Значение |
|---|---|
| DEPLOY_HOST | 178.208.64.38 |
| DEPLOY_USER | root, для существующей установки с Docker от root |
| DEPLOY_SSH_KEY | отдельный закрытый ключ для выкладки; не ключ обычного личного доступа |
| DEPLOY_KNOWN_HOSTS | запись known_hosts для 178.208.64.38 с проверенным ключом хоста |

Используется SSH-порт 22. BOT_TOKEN, пароли панели и базу в GitHub не переносить: они остаются в серверном .env/data. Закрытый ключ не присылать в чат и не коммитить. Ветка PR не получает deployment secrets при обычных тестах.

Создание отдельного ключа на своём ПК и добавление его открытой части в authorized_keys сервера выполняется один раз. Перед настройкой сверить ключ хоста с выводом ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub, полученным через уже проверенный SSH. Не заменять это отключением StrictHostKeyChecking.

Ключ root даёт широкие права на сервер. Используйте отдельный ключ только для этого репозитория/окружения; при передаче сопровождения отзывайте его отдельно. Более ограниченная сервисная учётная запись требует отдельной настройки серверных прав и deploy.sh; этот вариант не заявлен как уже выполненный.

Настройку environment/secrets и ключей пользователь должен выполнить в своих интерфейсах. Наличие файлов workflow не означает, что доступ к серверу уже настроен.

## Порядок выпуска

1. Отдельная ветка и PR, проверка CI и изменений.
2. Объединение в main.
3. Actions → Deploy production → Run workflow → main.
4. Дождаться checks, подтверждения production при его настройке и deploy.
5. Проверить https://178.208.64.38 и /start, затем целевой сценарий.

На сервере скрипт:

- блокирует параллельную выкладку;
- требует неизменённые отслеживаемые файлы; локальный .dockerignore остаётся допустимым;
- получает main и проверяет, что указанный SHA входит в его историю;
- отказывается от обычной выкладки при изменении app/models.py или app/db.py: для таких изменений нужен отдельный план миграции;
- создаёт копию штатным установленным /usr/local/sbin/equipment-backup.py до изменения исходников;
- сохраняет прежний Docker-образ, переключает исходники на точный SHA и строит новый образ, пока старый контейнер работает;
- пересоздаёт только сервис equipment-bot с действующим full.yml и постоянным data/;
- проверяет /login и работу процесса;
- при ошибке возвращает прежние исходники и, если контейнер уже менялся, прежний образ.

Полная логика миграций по двум именам файлов не определяется: это дополнительная преграда, а не гарантия совместимости. Даже если эти файлы не менялись, изменения данных и миграции необходимо отдельно проверять при ревью.

Откат не восстанавливает базу автоматически. Если новая версия изменила данные, одного отката образа может быть недостаточно. Копия создаётся заранее, восстановление выполняется по отдельному решению с учётом потери новых записей.

Короткий перерыв при пересоздании единственного контейнера ожидаем. Незавершённые диалоги бота хранятся в памяти и сбрасываются при перезапуске. HTTP-проверка не заменяет реальную проверку /start и сообщений.

Успешная выкладка оставляет Git в detached HEAD на проверенном SHA. Это ожидаемо. Обычные команды compose с full.yml используют обновлённую стандартную метку образа. Для ручного возврата к работе с main сначала проверить состояние, сохранить копию и явно переключить ветку.

Версионные Docker-образы не удаляются этим скриптом: контролируйте df -h и docker system df. Не запускайте общую очистку Docker ради этого проекта без проверки других сервисов.

## Первая проверка на действующем сервере

До первой выкладки на этом сервере подтверждены main b1c82bf, полный режим, локальная публикация порта, .dockerignore и установленный скрипт копирования. Проверка новых workflow и deploy.sh должна быть зафиксирована отдельно после их реального выполнения. Нельзя считать статическую проверку shell-синтаксиса успешной выкладкой.

Для ручного запуска того же скрипта после получения и проверки новой версии: bash scripts/deploy.sh ПОЛНЫЙ_SHA. Не использовать непроверенные ветки в production. Действующий бот до этого работает в прежнем контейнере.

## Изменение поля времени

Стандартный input time заменён на два обязательных списка: часы в 24-часовом формате и минуты. Внешний вид больше не зависит от 12-часового формата устройства. Ограничение 07:00–22:00 сохранено; например, 22:01 отклоняется сервером с объяснением. Сохранённое время снова выбирается при открытии карточки; старые открытые формы с issue_time продолжают обрабатываться. Дата, база и формат времени в сообщении студенту не меняются.
